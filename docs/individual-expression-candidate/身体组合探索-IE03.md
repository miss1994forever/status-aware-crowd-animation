# IE-03：身体目标与受约束的组合求解

2026-11-05。延续用户“探索更有效的身体组合表达方式”授权；用户随后追问是否应有比线性更合理的status调节、目前是什么算法。当前优先区分表达目标的语义依据和姿态执行的几何依据；不能以更复杂求解掩盖status映射尚未验证。

## 目前与新增原型的区别

用户已看的IE-02页面只有手臂消融：`c=1-status`，速度权重、.20秒滤波、姿态门控、定长弧与9°上限。执行有非线性，语义仍是简单源动作到收束的创作映射。用户明确反馈未感觉到差别。

IE-03新增独立的 `BodyCombinationSearch`：status仍通过明确profile给出期望表现，**不凭空新增某条“科学非线性地位曲线”**；求解器针对目标身体高度/肘部外侧占用，在当前源姿态和约束中选择实际幅度。它改变的是如何协调执行目标，不声称解决了目标的心理学意义。

两个组合：A直接按同一表达权重叠加高度与手臂；B目标＋约束组合。B不额外缩小矢状摆臂、不新增前倾/昂头/改步速。初步提到的摆幅路线已因用户对语义映射的追问而暂缓，未加入当前实验。采用A作对照可检查新的求解是否只是增加复杂度。

## 输出目标与求解

输入只用自己的作者设定、源姿态、真实根速度、尺度和时间，不读取别人status。profile目前仍为SourceToCompact，表达强度经原策略平滑后为w。

- 期望降低：`h*=.0125*bodyScale*w`，延续历史组合的相近幅度；不为可见性任意放大。
- 期望手臂空间占用：在源向下/向外上臂上，目标外侧单位分量为 `x*=x*(1-.40*w)`。不是直接规定肩关节必须转几度；动作门控或角度上限可能导致目标未满足。
- 其他优先项：原动作偏离、额外膝弯、参数时间变化。不会把腿部受限的差额转移到更大夹臂。

宿主通过evaluate(height,armWeight)提供实际姿态特征和约束结果。求解器比较25组幅度（高度/上臂均在0到期望幅度的四等分点），最小化：高度目标偏差²＋肘部目标偏差²＋.20膝部改动代价²＋.10手臂改动代价²＋.10参数时间变化代价²。高度归一化容差为.003身体尺度；肘单位分量容差.04；其余使用12°膝/9°臂归一化。

这些权重和容差全是工程选择，没有感知标定。25点仅是低维有界近似，不声称全局最优或全身运动优化。选定后对参数作.10秒指数平滑，再重新检查可行性；不混合骨架位置。平滑结果不满足约束时退回可行候选，并记录TemporalFallback。

非线性来自源姿态到空间特征的几何关系、姿态门控、限幅、候选竞争和约束；它有机械上的理由，不能自动赋予status语义。

## 高度真正执行与腿部边界

离线回放链接编译只读 `reference/SprintLegIK.cs`，原文件哈希不变，调用其Knee函数；没有另写或修改空间线膝盖算法。为了在不启动Unity的情况下执行，测试目录实现最小UnityEngine托管数学兼容层。兼容层不是引擎，未证明与Unity数值行为等价；本结果只能用于组合探索，不能继承为空间线的膝部验收。

原冻结坐标是参考身高单位。回放临时换算到**声明的虚拟1.65米角色**以使用原源码绝对阈值，结束后换回原显示单位；不是将原BVH单位或演员身高声称为已知。前方符号由整段源腿部可见弯曲方向确定，避免左右骨骼命名/坐标手性的歧义；没有使用status。

保持源脚与所有脚后代位置；身体平移、双腿膝位求解后检查骨长。目标组合还限制新增大腿方向变化不超过12°。这些不是动力学、全身碰撞、手接触或真实脚接触保证。

## 当前检查及问题

两段原FK共330帧，骨长误差约7e-7虚拟米，脚及脚后代位置误差0；目标组合最大额外膝方向变化约11.9°，最大降低约参考身高1.24%。均未触发参数平滑可行性回退。直接组合A在本两段样本也未触发这些硬门槛，因此不能宣称B必要或更好。

**连续性风险仍在：**源姿态差分扣除后的最大叠加关节步移约参考身高2.4%/帧。测试只设置3.5%排查极大跳变，不能把“未触发”写成自然度或膝连续性通过。来源是复用求解与源膝姿态共同作用；本线不继续改膝盖。若观看发现明显弯腿跳变，此组合不得合入，应由空间线串行处理或保留不降低版本。
